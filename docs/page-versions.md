# コマの保存（版ストア）

アニメ（最大 24 コマ）に備えて、作品の保存の形を変える。2026-09-11 決定。
アニメの画面より先に、今の 1 コマのままでこの作り替えだけを終わらせる。

## なぜ作り替えるか（実測）

作品は「丸ごと 1 レコード」で `works` に入っている。ページの絵も「前に戻す」用の控え
（最大 40 件）も、同じレコードの中に Blob として入る。これを 24 コマにしたときの保存を、
実測ページ（コマ保存ベンチ）で Chromium と iPhone Safari の両方で測った。

| | 1 レコードのまま 24 コマ | コマを別に置く |
|---|---|---|
| Chromium | 保存 23ms。開いた直後の保存で作品まるごと（約 8MB）が 1 回余分にコピーされる（次に DB を開いたとき回収） | 1.1ms |
| iPhone Safari | **22ms → 140ms と回を追うごとに伸びる** | 2〜3ms で一定 |

Safari の伸びはレコード内の Blob 参照の数に比例していた（1 個あたり約 0.4ms）。
控え 40 件 × 24 コマ × 2 枚 ≒ 2000 参照まで溜まると、自動保存 1 回が 0.8 秒前後になる見込み
（外挿）。描いている手が止まる長さなので、1 レコードのままでは成立しない。

なお Safari の `navigator.storage.estimate()` は Blob の中身を数えないので、Safari で
「同じ絵が二重に保存されているか」は測れない。別に置く方式ならその問いがそもそも起きない。

## 形

画像は **書き換えずに版を足していく**。モデルの「画像 Blob は不変なので参照を共有してよい」
（`snapshotOf()`）という約束を、保存の形にもそのまま通したもの。

- **版**（`PageVersion`）… あるページのある時点の絵。一度書いたら書き換えない。
  `{ versionId, workId, pageId, image, layers, activeLayerId?, createdAt }`
- **作品の行** … ページも控えも、画像ではなく `versionId` だけを持つ
  （`{ id, deleted, versionId }`）。封筒の `version` は **2**。
- 作品と控えのサムネイル（幅 360）は作品の行に残す。控え 40 件で約 40 参照＝Safari で約 16ms。
  問題になったら版の側へ移す。

保存先は同じサイトの IndexedDB の中に箱を 1 つ足すだけ（端末の中・同じ容量枠・
`requestPersistentStorage()` もサイト単位で効く・消えるときは全部まとめて消える）。

| DB | store | キー | 索引 |
|---|---|---|---|
| `iroha-paint`（既存・**バージョンは上げない**） | `works` | `work.id` | ― |
| `iroha-pages`（新規） | `versions` | `versionId` | `workId` |

### 画面側から見た形は変えない

`WorkStore` の約束（`put / list / listDeleted / get / setDeleted`）は変えない。組み立てと
分解は保管場所の中で行うので、`main.ts` とギャラリーには今までどおり画像入りの `PageData`
が渡る。増えるのは `PageData.versionId`（必須）だけ。`MemoryWorkStore` はオブジェクトを
そのまま持つので変えない。

## 版 ID の規則

**中身が同じ間は同じ ID、中身が違えば必ず別の ID。** 保存は「まだ無い版だけ書く」ので、
この規則が崩れると別の絵が同じ ID で握りつぶされる。

- 絵を焼き直したら新しい ID（`save()` がページを焼くたび。今は常に 1 コマなので保存のたびに新しい版）
- 焼き直さない保存（紙の種類を変えた・控えを撮った・ゴミばこへ入れた）は ID をそのまま使う
  → 控えは参照のコピーだけで済む
- 古い形（封筒 1）を読むときは **読むたびにランダムな ID を振る**。ページ id から作る
  決定的な ID にはしない。古いコードが同じ作品を封筒 1 で上書きし直すことがあり、そのとき
  「同じ ID で中身が違う」版ができてしまうため（重複は次の保存の掃除で消えるので害は無い）
- 古い形を読むとき、同じ Blob を共有していたページ（今のページと控え、控え同士）は 1 つの版に
  畳む。`image` と各 `layers[i].image` がすべて同一オブジェクトで、`activeLayerId` も等しいときだけ

## 書き込みの順番

2 つの DB をまたいで 1 回で書くことはできないので、**途中で止まっても欠けない順番**で書く。

1. `iroha-pages`：作品と控えが指す版のうち、まだ無いものだけ `add`（`getKey` で確かめる）
2. `iroha-paint`：作品の行を封筒 2 で `put`
3. `iroha-pages`：その作品の版（`workId` 索引）のうち、どこからも指されていないものを `delete`。
   **ただし作られて 10 分未満の版は消さない**

1 と 2 の間で止まれば、余った版が残るだけ（次の保存の 3 で消える）。作品の行が
まだ無い版を指すことは起きない。

- 同じ画面の中の `put` は **1 本ずつ順番に** 流す（自動保存と控えの撮影が重なると、
  片方の 3 が、もう片方が 1 で足したばかりの版を消しうるため）
- 10 分の猶予は、別のタブ・別のアプリ（ホーム画面から開いたままの共用 iPad 等）が
  同じ作品を同時に保存したときの保険

## 読み込み

- 封筒 1 … 今までの `unwrap()` どおりに補って読み、上の規則で `versionId` を振る。
  次に保存したときに封筒 2 へ移る（**作品は保存されたときに 1 つずつ移る**。一斉には移さない）
- 封筒 2 … `iroha-pages` からその作品の版を `workId` 索引でまとめて読み、組み立てる
- 封筒 1・2 以外 … 今までどおり読まない（壊れたデータで起動しない）
- `list()` は版を 1 回の `getAll` で読み、作品ごとに振り分けて組み立てる
  （今の `works` の `getAll` と同程度の読み取り）

### 版が欠けていたとき

書き込みの順番から起きないはずだが、起きても **作品を隠さない**。

- 控えの版が欠けていたら、その控えだけ落とす
- 今のページの版が欠けていたら、版が揃っているいちばん新しい控えの姿を今の姿として読む
- それも無ければ読まない（今の「壊れたデータ」と同じ扱い）

## 古いコードとの共存

作品の DB のバージョンを上げないのはこのため。上げると、更新前のコードのまま眠っていた
アプリ（ホーム画面から開いたままの共用 iPad）が復帰したとき DB を開けなくなり、
再読み込みするまで保存が黙って失敗し続ける。

- 古いコードは封筒 2 の行を `unwrap()` で読まない → 移った作品が一覧に出ない（再読み込みで戻る。消えはしない）
- 古いコードが封筒 1 で上書きしても、新しいコードは封筒 1 を読める → 失われない。
  次の保存で封筒 2 に戻り、使われなくなった版は掃除される

## テスト

vitest には IndexedDB が無いので、分解・組み立て・掃除の判断を純粋な関数に切り出して固める。

- 分解 … 作品 → 作品の行 ＋ 版の一覧
- 組み立て … 作品の行 ＋ 版 → 作品（欠けていたときの扱いを含む）
- 古い形の読み込み … 同じ Blob を共有していた控えが 1 つの版に畳まれる／読むたびに ID が変わる
- 掃除 … どこからも指されない版だけが対象になる／10 分未満の版は対象外

IndexedDB を通した動作（既存作品が移る・前に戻せる・ゴミばこから取り戻せる・保存時間）は
実機（Chromium と iPhone Safari）で確かめる。

## 手順

1. データの形と変換：`PageData.versionId` と上の純粋な関数、テスト
2. 保管場所：`IndexedDbWorkStore` を新しい形にする（`WorkStore` の約束は変えない）
3. 保存処理：`save()` で焼き直したページだけ新しい `versionId` にする
4. 実機で確かめる
